# ADR - Manufacturing Phase 3: production orders on the pending-document pattern

**Status:** accepted by the owner (2026-11-10); P3-1 (order core) implemented 2026-11-10. Follows `adr-manufacturing-service.md` (decision 5) and `adr-warehouse-upgrade.md` (W0-W6, the internal stock API this phase calls). Business detail: `docs/business/Manufacturing/ProductionOrders.md`.

## Context
Phase 0-2 gave Manufacturing its master data, bills of materials and routings. Phase 3 turns them into execution: a production order is created with a snapshot of the BOM and routing, scheduled, released (stock reserved), fed with material, reported by operation, receives finished goods and is completed and closed (spec `docs/business/M/02_PRODUCTION_DEV_TASKS.md` T3.1-T3.14). The spec assumed one database transaction with Inventory (BR-MAT-06, NFR-05); the Warehouse is another service with another database, so every stock effect is a call that can fail, time out or be repeated.

## Decisions (made with the owner, 2026-11-10)
1. **Pending-document engine.** A stock-affecting document (material issue / return / backflush, finished-goods receipt) is stored first as `Pending` with lines; each line is sent to the Warehouse under the key `<DocNo>#<line>` (the W5 contract: same key + same payload = the first result again, another payload = 409 `WH_IDEMPOTENCY_CONFLICT`). When every line is `Posted` the effect on the order (IssuedQty, CompletedQty ...) and the document status change in **one local transaction**. A transient failure leaves the document `Pending` (HTTP 202); a Warehouse refusal compensates the lines already posted (the opposite movement under `<DocNo>#<line>R`) and the document becomes `Failed` with the mapped `MFG_*` code. (P3-3)
2. **Retry job** (hosted, cross-tenant, one row claim per document with `FOR UPDATE SKIP LOCKED`): posts `Pending` documents older than 20 s with exponential back-off, 12 attempts, then `Failed (retries exhausted)`; manual retry by permission; a Pending document blocks Cancel / Unrelease / Close of its order. (P3-3)
3. **The effect of a document on the order is applied only when it is Posted.** An operation report with backflush lines waits for them. (P3-3/P3-4)
4. **Reservations: call first, then commit; both calls idempotent.** Release reserves in the Warehouse, then changes state; Unrelease / Cancel / Complete change state with a `ReservationReleasePending` flag, then release; a sweeper finishes what is left. Changing the quantity = release the remainder + reserve again (the Warehouse has no "adjust"). (P3-2)
5. **Domain events through an outbox** to Kafka topic `manufacturing-topic` (spec §8.1), written in the same transaction as the change, published by `OutboxProcessor`; no consumer in Phase 3 (costing is Phase 6). (P3-1, done)
6. **`Idempotency-Key` header** on the POST of issue / return / report / receipt, stored on the document. (P3-3)
7. **Scheduling:** infinite capacity; backward from the due date over the work centers' calendars, forward from now (and `IsLate`) when the start would lie in the past; no routing = the item's fixed lead time in working days on the plant calendar. (P3-1, done)
8. **Backflush moves into Phase 3** (owner): cumulative formula `ROUNDUP(output x Required / OrderQty) - Consumed`, lots first-expiry-first from the Warehouse suggestion, a shortage rejects the whole source transaction (`MFG_MAT_008`) unless the plant allows negative stock. Reversals stay Phase 4. (P3-4/P3-5)
9. **Serial-controlled items are refused** (`MFG_MAT_011`, new code): the Warehouse cannot move them yet (R206).
10. **Interim quality release** (owner): `manufacturing:qc:disposition` books the Warehouse `QcRelease` for a received lot until FQC inspections exist (Phase 4). (P3-5)

## Decisions taken while planning P3-1
1. **"Today" and "now" are the plant's**: `TimeProvider` injected, `PlantClock` converts with the plant's time zone; due dates, document-number months and the schedule use plant time; times are stored in UTC.
2. **BOM / routing choice (BR-PO-04):** a chosen version must be Approved and effective on the reference date (`MFG_PO_005`); the default is the version effective on the reference date, which is plant today for a new order and the old plan-start date (if still in the future) for a Draft that is regenerated; none = `MFG_PO_004`.
3. **Issue method = the BOM line's value.** The spec chain "BOM line -> item profile -> plant default" cannot be applied: a BOM line always carries Manual or Backflush, there is no "inherit".
4. **Quantity** must be > 0 with at most the decimals of the item's base unit (TC-PO-003); priority 1..5.
5. **Order numbers are unique per tenant** (one counter per tenant, document type and month; plant = `Guid.Empty`), deviating from BR-GEN-04 which counts per plant: the number is the idempotency key in the Warehouse (`<DocNo>#<line>`, unique per tenant, product and type), so two plants issuing `MO-2611-00001` would collide there. Found by the live check (two plants of one tenant). The counter increments outside the order's save, so a failed save leaves a gap (allowed by the spec).
6. **Draft regeneration** retires the old child rows (`IsDeleted`) and adds new ones; unique keys of the lines are filtered on `IsDeleted = false`. Nothing may refer to Draft lines (P3-2 must keep that true).
7. **Open order (BR-SET-03 / BR-WC-03):** Released, InProgress, OnHold (it was released) and Completed count; Draft, Closed and Cancelled do not. The guard is a real query now (`OrderBackedOpenOrderGuard`); the work-center and reason reference checks include orders.
8. **Warehouses of an order** default to the plant's raw-material (materials) and finished-goods (output) warehouses; an override must be one of the plant's own.

## Decisions taken while planning P3-2 (2026-11-10)
1. **Reservations are kept in line by a reconciler, not by "call first, then commit"** (this refines decision 4). The order commits its new state together with `ReservationSyncPending = true`; then `IOrderReservationSync` brings the Warehouse in line and clears the flag. Why: no orphan reservation after a failed local save; a Warehouse failure is a visible, retryable state (`reservationPending`), not a 5xx for something that was saved; release, unrelease, cancel and change of quantity use one idempotent routine. Reading availability to decide a **release** still needs the Warehouse: unreachable = `MFG_INT_001`, nothing changes (fail closed).
2. **The routine converges:** desired reservation = while Released / InProgress / OnHold, per material min(still needed, allocatable + what the order already holds), otherwise none. If the Warehouse already holds exactly that, adopt it; otherwise release it and reserve again (`SourceLineId` = the material line id). Warehouse refusal or outage records the error and a back-off (15 s doubling to 5 min); a hosted `ReservationSyncJob` (every 15 s, cross-tenant, one tenant scope per order) retries forever.
3. **Allocatable** = lot-less stock + lots with status Available and not expired in the material's warehouse, capped by the item's available quantity (the Warehouse's `LotPicker` rule, repeated on this side).
4. **Release** is allowed only for a Draft, checks plant / item / components / work centers active and no serial items, and honours `BlockReleaseOnShortage`; the first operation is Ready (all Ready if sequential execution is off).
5. **Unrelease and cancel** only while the order is untouched (`IOrderTransactionGuard`: state based now, pending stock documents added in P3-3); cancel needs a Cancel reason, hold a Hold reason (`MFG_PO_009`).
6. **Change of quantity** recomputes from the stored BOM (`OrderSnapshotBuilder.RecomputeForQuantityAsync`: required matched by component, outputs by item and type, operation minutes from the operation's own stored times via `IOperationTimeService.BuildInputsAsync(sources)`, new schedule) and keeps issued quantities.
7. **Plant deactivation is not guarded by open orders** (the specification guards only the costing method and work centers); recorded as a risk, not changed here.

## Decisions taken while planning P3-3 (2026-11-10)
1. **Engine shape.** A stock document is a header with lines; **each line is one Warehouse movement** (`MaterialTransaction` / `MaterialTransactionLine`). `StockPostingService` is the generic algorithm (forward, rollback), so receipts (P3-5) and backflush (P3-4) reuse it. Document `Pending` -> `Posted` | `Failed`; `Mode` Forward | Rollback; line Pending -> Posted | Refused | Compensated.
2. **Validate first, store second.** Everything this service can know is checked before a document exists; a violation is a plain 400 and stores nothing. A document is stored only for requests that look valid; a Warehouse refusal found while posting makes it `Failed` (kept for audit). Consequence: an *issue* reads availability and the reservation first, so with the Warehouse down it is refused (`MFG_INT_001`, fail closed); a *return* needs no Warehouse read and is accepted `Pending`.
3. **Posting algorithm.** Per line: build the request (lot / serial flags from Product), `RecordMovementAsync`, save the line at once. Transient (`MFG_INT_001`, 409 without code) = the document stays Pending with a back-off (10 s doubling to 5 min), never failed by counting; refusal = reverse the posted lines (`<key>R`) and `Failed`; `WH_IDEMPOTENCY_CONFLICT` = error log + `Failed`; reservation problems on a reserved line (`WH_RESERVATION_*`) = the line is taken from free stock once (key + `F`; safe because the Warehouse looks at the key first, so nothing was booked). When all lines are posted one save applies the effect on the order, sets `Posted`, writes the event and flags the order for a reservation sync. A save conflict leaves the document Pending (all lines Posted) for the next round - a fresh context, nothing is sent twice.
4. **Split of an issue line**: reserved part = min(quantity, what the order's reservation line still holds), the rest from free stock (needs a lot for lot-controlled items); stored on the lines so retries send identical quantities.
5. **Return**: to the material's warehouse, lot named for lot items, limits per material and per lot from posted + pending lines, cost = weighted average of the posted issues.
6. **Reservation in line before an issue (R218)**: if the order is flagged the handler runs the sync inline; still flagged = `MFG_MAT_012` (nothing stored).
7. **Retry job** `StockPostingRetryJob` (10 s, cross-tenant, tenant scope per document). It **claims** a document by pushing `NextAttemptAt` 2 minutes ahead and saving: the document's `xmin` makes a second instance lose the save. This replaces `FOR UPDATE SKIP LOCKED` of the master plan (same effect, no raw SQL, testable). A new document is stored with `NextAttemptAt` = now + 20 s so a dead request is picked up. Exits: `retry` (post now) and `abandon` (rollback, then Failed), permission `stock-document:retry`.
8. **Guard (R223)**: `OrderTransactionGuard` also counts a Pending document; unrelease and cancel are refused while one exists.
9. **`Idempotency-Key`** header on issue and return: stored with a hash of the request, unique per tenant; same key + same request = the first document; same key + another request = `MFG_GEN_007`; a parallel post loses the unique index and reads the winner.
10. **Document numbers `MI` / `MR` are per tenant and month** (like orders): the number is the Warehouse key (`<DocNo>#<n>`, unique per tenant, product and type).
11. **Posting date = plant today**; no back-dating before the period lock (Phase 6).

## Decisions taken while planning P3-4 (2026-11-10)
1. **Backflush is a stock document of type Backflush; the report is applied when it is Posted.** The report handler checks everything first (order and operation state, quantities, reasons, machine, input limit, and the **stock for the backflush**); nothing is stored when a check fails (a shortage is `MFG_MAT_008`, no report, no document, no movement). It then stores the `OperationReport` (Pending) and its `BF` document in one save and posts the document; when every line is in the Warehouse one save applies the document (`ConsumedQty`) and the report (operation figures, next-operation readiness, completion, `ScrappedQty`, first-transaction InProgress) and marks both Posted. A refusal during posting reverses the lines and fails document **and report** (kept, HTTP 400); an outage after the check leaves both Pending (HTTP 202) for the existing `StockPostingRetryJob`. A report with nothing to backflush needs no Warehouse and is applied in the save that stores it. This replaces the spec's "same DB transaction" (T4.1.3).
2. **Quantity (BR-MAT-08):** `ROUNDUP(cumulative output x Required / OrderQty, unit decimals) - recorded consumption`, never below zero (`BackflushCalculator`, pure). Cumulative output = (good + scrap) of applied and pending reports of the operation plus the new one; recorded consumption = `ConsumedQty` + backflush quantity on Pending documents. **Rework is not output.** Uses the current `Required` / `Quantity`.
3. **Stock split of a line** as for an issue (reserved part from the order's reservation, the rest from free stock), lots by first-expiry-first suggestion with one document line per lot; shortage = `MFG_MAT_008`, or with `AllowNegativeStockOnBackflush` a flagged last line sent with `AllowNegative` (not for lot-controlled items).
4. **Document model:** `StockDocumentType.Backflush`, `SourceOperationReportId`, line `IsNegativeStock`, `IsConsumption` (issue or backflush) drives key suffix / request / reversal building, prefix `BF` (per tenant and month, the Warehouse key), event `MaterialBackflushed`, `StockCodeMapper.ToMfg(code, type)` maps `WH_INSUFFICIENT_*` to `MFG_MAT_008` for a backflush. `StockPostingService` applies / fails the report together with the document.
5. **Time logs are their own aggregate** (`LaborTimeLog`), one per employee session; the operation status follows them (Running / Paused / Ready; a paused log stopped walks Paused -> Running -> Ready). Overlap is checked per employee, an open log runs to the end of time. The labor rate of the day (`ILaborRateResolver`) is stored on the log. The caller names the employee (validated active in MasterData).
6. **Report rules in order:** order open (OnHold `MFG_PO_011`, other `MFG_OP_001`), operation not Pending, quantities and reasons, machine, **input limit** (first operation `Quantity x (1 + over-production tolerance)`, later ones the cumulative good output before, pending reports counted), then a Completed operation `MFG_OP_009` - so an amount that also passes the input is `MFG_OP_004` (TC-OP-013). A report needs no time log and leaves a Ready operation Ready.
7. **Completion:** pure walk down the route after each report or manual completion (previous done or first, planned input taken); completing closes the operation's open logs. Manual complete: Ready / Running; reopen: Completed -> Ready while the next operation has no work (`MFG_OP_007`).
8. **Hold** pauses Running operations and the running logs in the same save; resume of the order restarts nothing.
9. **Report numbers `OR` per plant and month** (BR-GEN-04) with a unique index per plant; `MI` / `MR` / `BF` stay per tenant (the number is the Warehouse key).

## Consequences
- Manufacturing and the Warehouse are never one transaction: a `Pending` window exists in which a document is not yet in the order's figures; the UI says so (P3-6).
- Every Warehouse call of Phase 3 is safe to repeat; the cost is the engine (P3-3) and a background job in a service that had none.
- P3-1 adds the first Manufacturing outbox, the first hosted service and the first Kafka producer of the service; the topic has no consumer yet.
- P3-2 adds the second hosted service (`ReservationSyncJob`) and the first Manufacturing -> Warehouse calls in production use; a Released order may be briefly not fully reserved (flag), which P3-3 must respect when issuing.
- P3-3 adds the third hosted service (`StockPostingRetryJob`) and the engine every later stock document (backflush, receipts) reuses; the order never shows stock the Warehouse has not booked, at the price of a visible Pending window.
- P3-4 reuses the engine for backflush: a report with backflush is invisible (Pending) until the Warehouse has booked it, and its limits already count it; time logs and reports without backflush need no Warehouse.
- Behaviour that differs from the spec is listed in `docs/business/Manufacturing/00_Mapping-to-ERP.md`.
