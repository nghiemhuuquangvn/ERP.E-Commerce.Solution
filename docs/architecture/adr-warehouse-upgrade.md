# ADR - Warehouse upgrade for Manufacturing (decimal quantities, stock per warehouse and lot)

**Status:** accepted by the owner (2026-11-09); W1 (decimal quantities) implemented 2026-11-09; W2 (stock per warehouse and lot) implemented 2026-11-10; W3 (production movements, cost on the movement, idempotency) implemented 2026-11-10; W4 (reservations by source, partial consume, lot suggestion) implemented 2026-11-10; W5 (internal stock API for Manufacturing) implemented 2026-11-10. **Decided by the owner (2026-11-09):** a new `StockBalance` table next to `Inventory`; all Warehouse quantities become decimal. **Why now:** Manufacturing Phase 3+ (issue, return, receipt, backflush, QC hold, genealogy) needs stock per (item, warehouse, lot) in decimals, production movements and an idempotent write API (`docs/business/M/01_PRODUCTION_BA_SPEC.md` lines ~726-740, 673, NFR-05, BR-MAT-04/06/08; `docs/architecture/adr-manufacturing-service.md` decision 5).

## Where Warehouse stands (explored 2026-11-09)
- `Inventory` is keyed by **ProductId only** (no warehouse). Quantities are `int`; `Cost` is `decimal(18,2)` (weighted average only for `ValuationMethod = Average`). `InventoryLot` has int quantities, lot number, unit cost and expiry but **no** warehouse, status, manufacture date or unique lot number. `StockMovement` has an int quantity and **no cost** (cost lives only on the event). `Reservation` is keyed by `OrderId`.
- No `RowVersion` or lock anywhere; idempotency is a pre-check (`ExistsAsync(product, reference, type)`) without a unique index.
- `MovementType` 0-6; nine handlers create movements. Accounting posts from the event's `ValueDelta` and posts **nothing** for an unknown movement type.
- Internal endpoints: availability (Sales) and warehouse lookup (Manufacturing) only.
- Consumers of int quantities: Product (`Product.StockQuantity`), Purchasing (StockAlert), Sales (client, saga, returned-event mirror), Reporting, POS, Shipping; WH's own PO consumer casts decimals to `int`. No shared contract holds them; each consumer mirrors the event.
- Product has no lot / serial-controlled flags.

## Decisions
1. **`StockBalance`** `(TenantId, ProductId, WarehouseId, LotId?)` with `Quantity`, `ReservedQuantity`, `LockedQuantity` `decimal(18,6)` and a `rowversion`; unique on the key. It is the source of truth for per-warehouse and per-lot questions. **`Inventory` stays the per-item total** that Sales, POS and Replenishment read, so those flows do not change.
2. **One write path.** A new application service `StockLedger` changes `Inventory`, `InventoryLot`, `InventoryLocationStock`, `StockBalance` and writes the `StockMovement` in **one database transaction**. The nine existing handlers move onto it; an architecture test forbids mutating `Inventory` elsewhere. A parity test (sum of balances = inventory total) and `GET inventory/reconciliation` expose drift.
3. **Legacy stock without a warehouse** is assigned from `Location.WarehouseId`, else from the new inventory setting `DefaultWarehouseId`. The backfill report lists tenants where this is ambiguous (several warehouses, locations without warehouse); nothing is guessed silently.
4. **Lots:** `Status` (Available, QcHold, Blocked), `WarehouseId`, `ManufactureDate`, `Source` (Receipt / Production), unique `(TenantId, ProductId, LotNumber)` after a duplicate report. Releasing a hold is a `QcRelease` movement.
5. **Movement types** 7-12: ProductionIssue, ProductionReturn, ProductionReceipt, ProductionScrap, QcRelease, SubcontractTransfer. `StockMovement` persists `WarehouseId`, `LotId`, `UnitCost`, `ValueDelta`; the quantity sign convention is written down once; a filtered unique index `(TenantId, ProductId, Reference, MovementType) WHERE Reference IS NOT NULL` makes idempotency real. **Accounting posts nothing for the new types until Phase 6** (WIP posting keys); the event still carries the value. This gap between stock value and the ledger is a recorded risk.
6. **Decimals:** every quantity `decimal(18,6)`; stored unit costs `decimal(18,6)`, totals 2 decimals. Warehouse does not round quantities (the caller enforces UoM decimals). Events carry decimals. **Rollout order: consumers first** (they read decimals and still accept integers), then Warehouse; an old consumer reading `2.5` into an `int` fails.
7. **Reservations by source:** `SourceType` (SalesOrder default, ProductionOrder), `SourceId`, `WarehouseId`, line `SourceLineId`. Sales keeps `OrderId`, so the order saga is unchanged. Per-line reserve, partial consume, release; `StockBalance.ReservedQuantity` follows.
8. **FEFO suggestion** `SuggestLots(item, warehouse, quantity)`: Available lots, not expired, free quantity above zero, ordered by expiry then received date. The sales reserve uses it too, so expired lots are no longer allocated (documented behaviour change).
9. **Internal write API** `internal/v1/stock/*`, `[AuthorizeInternalService("manufacturing")]`: suggest lots, availability by warehouse / lot, reservations (reserve / consume / release), movements (production types), lots (create, set status). Every write carries an **Idempotency key** (the Manufacturing document number); a repeat returns the first answer. Answers carry the movement id and the **unit cost**. Negative stock is refused unless the call says `allowNegative` (BR-MAT-08). The pending-document and retry pattern on the Manufacturing side belongs to Phase 3.
10. **Product flags** `IsLotControlled`, `IsSerialControlled` (exposed by `internal/v1/product-lookup`); a production receipt without a lot for a lot-controlled item is refused.
11. **Concurrency:** `rowversion` on `Inventory`, `InventoryLot`, `StockBalance`; `StockLedger` retries a conflict three times on a fresh read, then answers 409.

## Milestones
W0 this ADR · W1 decimal quantities end to end (SQL 010, consumers first) · W2 `StockBalance`, lot columns, `StockLedger`, Product flags (SQL 011) · W3 production movement types, persisted cost, unique idempotency index (SQL 012) · W4 reservations by source, partial consume, FEFO suggestion (SQL 013) · W5 internal write API and an MO-A cycle script · W6 DS-01 stock seed, documents, regression of every live script. Each milestone ends with tests, a live check on glcheck, BA documents and a report, and waits for the owner.

## Consequences and risks
Live int -> decimal migration on large tables (lock time, run in a window; every environment needs the script) · consumers deployed out of order break on decimals · two stores (`Inventory`, `StockBalance`) can drift if code bypasses `StockLedger` · legacy stock may be assigned to the wrong warehouse for multi-warehouse tenants · the ledger does not see production movements until Phase 6 · FEFO skipping expired lots changes sales reservations · Warehouse has no integration tests (live scripts stand in) · POS and Storefront keep showing whole numbers · Reporting history keeps its old precision.

## Tenant scope (owner, 2026-11-09)
The owner asked to build for the SYSTEM tenant as the standard and clone it to the tenants SYSTEM manages. The repository has no clone mechanism and no tenant parent / child model (`AuthTenant` has no `ParentTenantId`); WarehouseDB is one database for every tenant, so the W1 schema change reaches all tenants at once and was verified on the SYSTEM (glcheck) host. For W2+ the per-tenant baseline (default warehouse, lot rules) follows the existing `InventorySettingsService` pattern (a System singleton is the standard, a tenant row is created on first read and inherits, overridable). A real clone / managed-tenant hierarchy would be a separate Identity epic.

## W2 as built (2026-11-10)
- `StockBalance` + `IStockLedger`/`StockLedger` (Application/Services): the ledger changes Inventory, lots, bins and balances; handlers keep their document logic, movement, value, events and the single `SaveChangesAsync`. Nine write sites, Reserve, Release and the expiry job moved onto it; `NoStockMutationOutsideTheLedgerTests` keeps it that way.
- Refinement of decision 11: **no retry loop in the ledger** (owner choice): a RowVersion conflict becomes `ConcurrencyException` = HTTP 409 and the caller retries (event consumers redeliver). Proven live: two parallel sales of the last unit gave 409 + 201 and stock 0.
- Owner choice for legacy stock: the tenant's default warehouse (`TenantInventorySettings.DefaultWarehouseId`, else MAIN, else first active by code; none = "unassigned" rows with a NULL warehouse so old flows are never blocked). The warehouse table has no creation date, so "earliest" became "MAIN, else first code".
- Lot-less pools: an issue takes from the named warehouse first, then the others; a lot-less reservation is held on the lot-less balance. The legacy reserve still checks the item total.
- Not in W2 (moved): lot / serial enforcement on receipts (needs the product flags in the caller - W5), per-warehouse availability (W4), cost per movement (W3).

## W3 as built (2026-11-10)
- Enum 7-12 appended (ProductionIssue, ProductionReturn, ProductionReceipt, ProductionScrap, QcRelease, SubcontractTransfer); `Quantity` of these is always positive and the type gives the direction. `StockMovement` gains nullable `WarehouseId`, `LotId`, `UnitCost`, `ValueDelta`, `StockDelta` (`Describe(...)`); the 9 older write sites fill them too; older rows stay NULL.
- **Refinement of decision 4 (idempotency):** the live data holds 750 repeated (tenant, product, reference, type) groups, so the unique index covers only the production types: `UX_StockMovements_Idempotency (TenantId, ProductId, Reference, MovementType) WHERE Reference IS NOT NULL AND MovementType >= 7`. The key has no warehouse / lot (a receipt creates its lot id, so it cannot be part of a key known in advance): one reference = one line, `DocNo#line`. Replay = the handler finds the key first and answers the first result; a race reaching the index becomes `ConcurrencyException` (409) and the retry replays.
- `ProductionMovementService` (Application) sits on `IStockLedger` (new ledger operations `IssueFromLotAsync`, `ReturnToLotAsync`, `SetLotStatusAsync`, `MoveBetweenWarehousesAsync`); W5's internal API will call it. `RecordStockMovementCommand` accepts the six types through the existing endpoint. Unknown type / missing reference are `BusinessRuleException`.
- Cost rules: issue / scrap at the item average cost, or the lot's cost under FIFO / LIFO; return / receipt at the cost passed; QcRelease and SubcontractTransfer carry no value. A lot moves between warehouses only as a whole.
- Accounting: no posting for the six types; an Information log line per skipped movement. Reporting is unaffected (its warehouse consumer does not match `StockMovementRecorded`).

## W4 as built (2026-11-10)
- `Reservation` gains `SourceType` (SalesOrder 0 / ProductionOrder 1) and `SourceReference`; `OrderId` keeps holding the source document id, so sales code is untouched. `ReservedItem` gains `SourceLineId`, `WarehouseId`, `ConsumedQuantity`; `LotAllocation` gains `Consumed` (JSON; the mapping compares by content). Production reservations have no expiry and raise no integration event.
- Ledger: `ReserveForSourceAsync` / `AvailableInWarehouseAsync` (one warehouse, no fallback to others), partial `ConsumeAsync(item, quantity, lotId)`, `ReleaseAsync` frees only the remainder. `LotPicker` is the single first-expiry-first rule shared by the reservation and `SuggestLotsQuery` (Available, not expired, free quantity, optional warehouse). `ProductionMovementService` issues against a reservation when `ReservationId` is given.
- **R193 cause fixed:** `Inventory.SellStock` needs available stock and no longer lowers the reservation; `ConsumeReserved` is for shipments and reservation issues. The ledger's pool issue no longer lowers pool reservations either (found live). No data repair: the live seed data has ~1 000 unexplained `ReservedQuantity` values and repairing them would erase demo reservations.
- Behaviour changes: expired lots are no longer allocated to sales; manual sale / vendor return need available stock.

## W5 as built (2026-11-10)
- `InternalStockController` (`internal/v1/stock`, `[AuthorizeInternalService("manufacturing")]` on every action, MediatR only): availability, suggest-lots, reservations (make / read / release), movements, lot status. No schema change.
- **Idempotency key = the movement Reference `<doc>#<line>`**, format checked on the internal route (`WH_REFERENCE_FORMAT`). `ProductionMovementService` now compares the payload on a replay: same payload = first result; other quantity / warehouse / lot = `ConcurrencyException` carrying `ErrorCode = WH_IDEMPOTENCY_CONFLICT` (HTTP 409 with `errorCode`; a plain optimistic-locking 409 has no code and may be retried). `ERP.Shared` gained `ConcurrencyException.ErrorCode` and `GlobalExceptionMiddleware` writes it as `errorCode`.
- **Flags passed by the caller** (owner decision): `RequiresLot` / `RequiresSerial` on the request; the Warehouse does not call Product. Serial-controlled items are refused (`WH_SERIAL_NOT_SUPPORTED`, owner decision: per-serial tracking is a separate epic); lot-controlled items need a lot number on receipt and a named lot on return / scrap / transfer / issue (an issue against a reservation may draw lots only).
- `SetLotStatusCommand` (QcHold / Blocked; release stays the QcRelease movement), `ReleaseReservationCommand` made idempotent (a reservation that is not open is answered as it is; unknown id = 404 instead of `InvalidOperationException`).
- Manufacturing: `IWarehouseStockClient` / `WarehouseStockClient` (no cache, 15 s, uncoded 409 retried 3 times) and the dev-only `seed/stock-cycle` runner (`Manufacturing:EnableDemoSeed`).
